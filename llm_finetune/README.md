# Fine-tuning an open LLM for the copilot's grounded answers, then serving it with vLLM on a T4

**STATUS: not yet run on a GPU; no accuracy or throughput numbers.** What has run is listed under
[What was verified locally](#what-was-verified-locally): the dataset build, the scorer (with real numbers for the
app's own offline generator), the endpoint evaluator against a stub server, and the whole notebook as a CPU smoke test
with a 0.5B model and a stub server in place of vLLM.

## Purpose

The app already talks to any OpenAI-compatible endpoint (`backend/app/llm.py`, provider `openai_compat`, used for
NVIDIA NIM, vLLM and Ollama). This folder adds the other half: an open model **trained for the app's own task** and
**served efficiently on a GPU**, measured with the app's own checks.

1. `make_dataset.py` builds supervised examples for the Ask task (`POST /api/ask`, the grounded answer with
   citations) by running each question through the app's own planner, tools, hybrid retrieval, access control,
   prompt-injection quarantine and PII redaction, and capturing the exact request the app sends to a model.
2. `sales_llm_qlora_vllm.ipynb` (generated by `build_notebook.py`, data embedded) QLoRA-fine-tunes
   `Qwen/Qwen2.5-1.5B-Instruct` on a free Kaggle or Colab T4 with transformers, peft, trl and bitsandbytes, evaluates
   base vs fine-tuned on a frozen test set, then serves the merged model with vLLM and compares fp16 with a 4-bit
   GPTQ variant (tokens/s, latency p50/p95 at concurrency 1, 8 and 16, time to first token, peak GPU memory), and
   tensor parallel 2 vs 1 when the session has two GPUs.
3. `eval_endpoint.py` scores any OpenAI-compatible endpoint on the same frozen test set through the app's own
   `OpenAICompatProvider`, either with the frozen prompts or end to end through the unchanged app.

## The task and how the data was made

**Task.** For `POST /api/ask` the app sends the model a system prompt and a user message holding the task
instruction, the seller's question, the `Answer` JSON schema and the evidence the caller may see, each item wrapped in
`<evidence id=...>` tags with personal data replaced by placeholders such as `[PERSON_1]`. The model must answer with
`{"answer": ..., "claims": [{"text": ..., "source_ids": [...]}]}`, cite only supplied ids, and, "if the evidence does
not contain the answer, say so and return an empty claims list".

**Examples.** 24 question intents, each with four wordings: 20 intents about a fact held by one structured record
(deal stage, amount, close date, win probability, products, competitor, next step, pain point, demo feedback, open
question, deal risk, deal-desk discount guidance, next meeting, owner, city, headcount, use case, tier, a contact's
name by job title, a contact's email) and 4 about facts no record holds (revenue, CEO, stock ticker, ERP system).
Every intent is asked about every account by an SDR, an AE and a sales manager of that territory, and four intents
also by an AE from another territory. Personas come from `users.json` where one exists; otherwise a dataset-only
persona with the same role is used (for example an SDR for EMEA-North), because the access policy in
`app/security.py` applies to any user object. Out-of-territory questions in training are asked by a persona whose
territory has no accounts (`ds-ae-latam`), so that no record of a validation or test account can enter a training
prompt; validation and test use real AEs from another territory, whose evidence holds other accounts' records.

**Pipeline.** Each question goes through `Agent.ask` with the offline provider and the default hash embedder,
exactly as in the app. The `answer` request is captured unchanged (`system`, `prompt`, redacted evidence). The
redaction mapping is rebuilt and checked against the captured evidence so that placeholders in the targets are the
ones the model sees.

**Targets: deterministic, from the structured records.** If the evidence this persona received holds the fact
(matched in records of the same account, ignoring quarantined items), the target states it in a fixed sentence and
cites up to two evidence ids that hold it; personal data appears as placeholders (`The VP Operations at Velmora
Logistics is [PERSON_1].`), which the app restores for the authorised user. Otherwise the target is the app's own
abstention (`I could not find this in the records you are allowed to access.`, empty claims), and the reason is
recorded: the persona's role cannot read the record type, its sensitivity is too high, the territory is not the
persona's, the app did not retrieve a readable record, or no record holds the fact.

Why deterministic targets and not a teacher model (for example `openai/gpt-oss-120b`, filtered by the app's
validators):

- **Correct by construction.** Every fact is copied from the record field that holds it, and the citation is that
  record. The app's validators check JSON, citation ids and a word-overlap groundedness proxy; a fluent teacher answer
  that cites the right record but misstates the amount passes all three. Deterministic targets cannot.
- **The labels the test needs come for free.** The same construction gives each test row its gold fact, the ids that
  hold it and whether the right behaviour is to answer or abstain, so scoring needs no judge model.
- **Abstention is decided by what the persona may see.** The builder knows from the access policy and the captured
  evidence when the answer is out of reach; a teacher sees only the evidence and may answer from a near miss.
- **Reproducible and offline**, like the rest of the repo: no key, and `make_dataset.py --check` rebuilds the files
  byte for byte. A teacher on Groq's free tier (8,000 tokens per minute, prompts of about 1,000 tokens) would also
  have needed about two hours per few hundred examples and could not be re-run identically.

The cost: answers are template sentences and the question wordings are templates too, so the model learns this
house style and the text-overlap metric partly rewards it. The test set therefore reports a **held-out wording**
subset (one wording per intent is used only in the test set) and is built from **unseen accounts**, and the
metrics that matter do not depend on style: valid JSON, valid citations, the fact, and answering vs abstaining.

### Splits (numbers from `data/dataset_report.json`)

Accounts were assigned by seed before any training: test gets one account from each of APAC-West, APAC-South and
EMEA-North; validation one from APAC-West and one from NA-East; the other seven are training accounts.

| Split | Accounts | Rows | Answer / abstain | Abstain reasons: role / sensitivity / territory / no record | Wording |
|---|---|---|---|---|---|
| train | ACC-002, 004, 005, 007, 009, 010, 011 | 501 | 338 / 163 | 36 / 8 / 35 / 84 | seen only |
| validation | ACC-003, 012 | 151 | 105 / 46 | 11 / 1 / 10 / 24 | seen only |
| test (frozen) | ACC-001, 006, 008 | 237 | 164 / 73 | 16 / 6 / 15 / 36 | 118 seen, 119 held out |

No example needed the "not retrieved" reason: whenever the persona could read the record, the app's tools or

### Leakage checks (all in `dataset_report.json` under `leakage`)

- Test accounts never appear in training or validation; validation accounts never appear in training: 0 training
  prompts contain a record of, or name, a validation or test account (asserted at build time and in the tests).
- 0 prompts and 0 questions are shared between any two splits; the held-out wording occurs only in the test set.
- **Golden-eval protection**: 41 training and 3 validation rows were dropped because their target would teach the
  answer to a question in `backend/eval/golden.json` (same account, and the target contains that item's expected
  fact or a value a golden negative must not reveal). That keeps the app's evaluation gate clean if it is ever run
  in LLM mode with this model. 78 test rows overlap golden facts; they are only reported, since test rows are never
  trained on.
- 8 validation prompts contain records of a test account (out-of-territory questions whose evidence is another
  territory's records). Validation is used only for the loss that picks the checkpoint; reported, not removed.
- Shared vocabulary, reported: some test facts also occur in training targets because they are shared values such as
  stage names, tiers, the account owner (one AE owns accounts in several splits) or product names.

## Evaluation (the same code locally, in the notebook and in `eval_endpoint.py`)

Per test row, from the raw model output: **schema valid** (parses with `app.llm.extract_json` and validates as
`app.models.Answer`); **app accepts without retry** (passes `Agent._filter_citations` and validation); **behaviour**
(abstained = valid with an empty claims list, correct when it matches the row); **fact accuracy** on answer rows
(short facts: one accepted form as a substring, for example `USD 420,000` or `420,000`; long facts: at least 60% of
their content words, using the app's `terms`); **citation validity** (every cited id was in the supplied evidence and
the persona may read it, checked with the independent oracle in `backend/eval/run_eval.py`); **citation hit** (a
cited id holds the fact); the app's **groundedness proxy**; **ROUGE-L F1** against the target answer. Means come with
bootstrap 95% intervals (10,000 resamples of rows), and fine-tuned minus base with paired intervals. Results are
reported for all rows, seen vs held-out wording, answer vs abstain rows, and each abstain reason.

It always returns valid JSON with valid citations, because it copies sentences from the evidence. It abstains on

and it relies on word overlap, so a new wording more than halves its fact accuracy. The targets themselves score 1.0
on every metric (a self-check of the scorer). Both rows appear in the notebook's tables for comparison.

## Model and training

`Qwen/Qwen2.5-1.5B-Instruct`, revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306` (Hugging Face API: Apache-2.0,
not gated). It fits a T4 comfortably for QLoRA and for fp16 serving, emits JSON reliably and has a plain chat
template. `Qwen2.5-3B-Instruct` was not used: its licence is listed as "other" (Qwen research licence), not
Apache-2.0. The smoke test uses `Qwen/Qwen2.5-0.5B-Instruct` (revision `7ae5576...`, same tokenizer and template).

QLoRA settings (first code cell): 4-bit NF4 base with double quantisation and fp16 compute (bitsandbytes), PEFT
`prepare_model_for_kbit_training`, LoRA r 16, alpha 32, dropout 0.05 on all attention and MLP projections, 2
epochs, learning rate 2e-4 with cosine schedule and 5% warm-up, batch 2 x 8 gradient accumulation (effective 16, so
about 64 optimiser steps), fp16 autocast (a T4 has no bf16), loss on the answer tokens only, the checkpoint with the
lowest validation loss kept, seed 42, greedy decoding for evaluation. Two things found while building this:

- TRL 1.17.1 casts QLoRA adapter weights to bf16 (`trl/trainer/sft_trainer.py`, "When using QLoRA ..."). With fp16
  loss scaling on a T4 that would fail when gradients are unscaled, so the notebook casts the trainable adapter
  tensors back to fp32 after building the trainer and prints how many it recast.
- The adapter is trained against the 4-bit base but merged into the fp16 base, which is what vLLM serves. That is the
  usual QLoRA deployment path; the small mismatch is why the merged model is evaluated, not the 4-bit training model.

## Inference optimisation (vLLM)

- **vLLM 0.32.0** (released 18 October 2026), in its own virtualenv: it pins torch 2.13.0 and
  transformers < 5.20, which would break the training stack (transformers 5.22.2). The notebook picks the PyPI wheel
  (built for CUDA 13, needs an NVIDIA driver that supports CUDA 13) or, on older drivers, the `+cu129` wheel from the
  vLLM release page with torch 2.13.0+cu129. Both exist (checked on PyPI, the release page and the PyTorch index).
- **T4 support, checked in the 0.32.0 source**: Turing is supported in fp16 only (`--dtype half`; bf16 raises an
  error), attention runs on the Triton backend (FlashAttention needs sm80 and FlashInfer is gated to sm80 in this
  release), and the Marlin kernels are compiled for sm75.
- **Quantized variant: GPTQ W4A16** made with llm-compressor 0.12.0.3 from 128 training prompts (never test
  prompts), in a third virtualenv. Why: vLLM 0.32.0 lists GPTQ and Marlin as supported on Turing and its
  compressed-tensors W4A16 scheme needs compute capability 7.5; FP8 W8A8 needs Ada or newer; bitsandbytes moved to an
  out-of-tree plugin (`vllm-bnb-plugin`) in this release; AutoAWQ is archived, and llm-compressor's AWQ writes the
  same W4A16 format. llm-compressor 0.12.0.3 pins compressed-tensors 0.17.1, next to vLLM's 0.17.0 (later releases
  need 0.20). If GPTQ fails, the notebook serves vLLM's online FP8 (`--quantization fp8_per_tensor`; plain
  `--quantization fp8` no longer quantizes online in 0.32.0) and records which variant ran.
- **Tensor parallel 2 vs 1** when two GPUs are present (Kaggle T4 x2, PCIe, custom all-reduce disabled). For a 1.5B
  model, splitting across two PCIe GPUs is expected to cost more in communication than it gains; the run measures it.
- **What is measured** per variant, with the frozen test prompts sent like the app's `openai_compat` provider sends
  them (streaming, temperature 0, up to 320 new tokens): startup time, model weights memory and KV-cache capacity
  (from vLLM's log), output tokens/s and requests/s, latency p50/p95, time to first token p50/p95 and per-request
  decode speed at concurrency 1 (first 32 prompts), 8 and 16 (all 237), peak GPU memory (nvidia-smi, polled every
  0.5 s), and answer quality on the full test set (scored like the HF run, and compared with it). Every server gets
  the same fixed KV cache (4 GiB per GPU), so peak memory differs only by weights, activations and graphs.

## Caveats

- **Synthetic, templated data.** 12 fictional accounts, generated records, template questions and template answers.
  A gain here shows that the model learned this task format and this abstention behaviour on unseen accounts; it says
  nothing about real CRM data or real users' questions. ROUGE-L rewards the template wording, so the fine-tuned model
  is expected to win it easily; fact accuracy, citation validity and correct abstention are the informative metrics,
  and the held-out-wording subset is the honest headline.
- **The model never sees who is asking.** Access control happens before the prompt is built, so the model learns to
  abstain when the evidence does not hold the fact; it does not learn the policy. The access-denied abstentions are
  still the cases that matter most, because a model that answers them is inventing a value it was never shown.
- **Small test set from the same generator.** 237 rows from 3 accounts, built by the same pipeline and templates as
  the training data. Intervals are about plus or minus 0.06 on all rows and wider on subsets (16 rows for
  role-denied abstentions). One seed, one training run, greedy decoding.
- **Fact matching is a string check.** Short facts need an accepted surface form, so a correct answer phrased
  differently (for example "four hundred and twenty thousand dollars") is scored wrong. The "hidden fact in output"
  check is coarse: the one offline-generator hit is another account's "Proposal" stage, which happens to match.
- **The base model is not tuned to the app's conventions** (for example that an abstention is an empty claims list),
  although the prompt states them. Base vs fine-tuned shows what fine-tuning adds for this prompt, not how good the
  base model is in general.
- **Serving numbers are for a 1.5B model on a T4.** They show the method and the trade-offs (memory, throughput,
  latency) on cheap hardware, not what an 8B or 70B model does on an H100. The prompts share a long prefix (system
  prompt, task, schema), so vLLM's prefix caching, on by default, helps time to first token; outputs stop at the end
  of sequence, so tokens/s depends on answer length.
- **Not built**: TensorRT-LLM or NIM packaging of the fine-tuned model, a GGUF export, multiple seeds, a larger or
  hand-written test set, and preference tuning.
